## 3. Overall Assessment

The five plans are structurally sound: the section order, anchors, dependency table, line-numbered code links, and the one-to-one mapping between §2.1 and §6 are in place.
The two name index plans are not ready to start. Their generation and rename rules, their input points, and their stored columns leave correctness holes that can produce a usable index with missing rows, and their equality condition conflicts with the walk's limit.
The other three plans are close, but they leave stale current-state sentences and underspecify a few operational and gesture details.
We recommend revising `name-index-store` and `name-index-search` before implementation. The other three can start after the fixes listed for them.

### R-1. The Name Index Does Not Follow the Timeline's Generation and Sweep Rules

**Type: Design issue** / **Confidence: High**

**Location**

`NameIndex`'s operations at [Step 1 of `name-index-store`](../plans/name-index-store.md#s-1) (lines 93-99), the sweep call at [Step 3](../plans/name-index-store.md#s-3) (line 125), and the own-change calls at [Step 4](../plans/name-index-store.md#s-4) (lines 137-140).
The timeline precedent is [Timeline Design §6.1](../design/timeline.md#61-scanning-and-skipping-rereads) (lines 155-157), [§6.4](../design/timeline.md#64-the-daemons-own-changes) (lines 197-203), and [`TimelineIndex::apply` / `rename` / `sweep`](../../daemon/entrypoints/daemon/src/service/timeline/index.rs#L375).

**What is wrong**

`replace_children` takes a generation but does not say to use the larger of the passed generation and the current one.
`rename` and `remove` take no generation at all.
There is no equivalent of the timeline's negative generation for rows reassigned while a full scan is running.
The plan then calls `mark_usable` after the scan, so an index that lost rows to the sweep is certified as complete.

**Basis**

`TimelineIndex::apply` promotes an old range-scan generation with `generation.max(current)`.
`TimelineIndex::rename` sets a negative generation for reassigned rows, and `sweep` uses both the positive and negative cases.
The timeline has a test for "a stale generation does not make rows sweepable".
The plan's Step 3 passes the scan's generation to `replace_children` and `sweep` but never restates these rules.

**Impact**

A range scan that started before a full scan writes rows with the old generation; a full sweep can delete them.
A rename during a full scan can move a row that the sweep then deletes.
`mark_usable` has no way to detect either case, so search can be answered from an index that is missing rows until the next full aggregation.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1 as the generation contract.
The owning plan is revised before implementation: Step 1 defines the generation source and the reassignment rule, Step 3 uses the promotion rule, and Step 4 records the generation of a rename.

<a id="r-2"></a>
### R-2. The Name Index's Rename Does Not Handle Merges, Hidden Destinations, or Additions

**Type: Design issue** / **Confidence: High**

**Location**

[`NameIndex::rename`](../plans/name-index-store.md#s-1) (line 98) and the own-change step at [Step 4](../plans/name-index-store.md#s-4) (lines 137-140).
The contents rule is [Listing and Search Design §5.1](../design/listing.md#51-name-index) (lines 172-173).
The timeline's re-evaluation rule is [Timeline Design §6.4](../design/timeline.md#64-the-daemons-own-changes) (line 207).

**What is wrong**

The plan says only that rows under the source are reassigned to the destination.
It does not say to delete the rows already at the destination, to drop rows when the destination is hidden, or to add rows when a hidden entry becomes visible.
A folder merge can therefore collide with the destination's rows, a rename to `.photo.jpg` can leave hidden rows in an index that promises not to hold them, and a rename out of a hidden folder can leave the entry missing until the next scan.

**Basis**

The timeline deletes the rows remaining at the destination before reassigning, and its range aggregation re-determines the extension and hidden rules at the destination.
The timeline's test includes `photo.jpg` to `photo.txt` and `.photo.jpg`, and back.
The listing design says the name index holds only non-hidden Entries and the Entries inside them are not held.

**Impact**

The index can hold duplicate or hidden paths, or can omit an Entry that exists, while still being marked usable.
The delete/rename completion check in condition 2 does not cover these cases.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1.
Step 4 is revised to delete the destination's rows, drop hidden destinations, and add a visible destination when no rows exist; the mutation test covers the hidden round trip and a folder merge.

<a id="r-3"></a>
### R-3. A Single-File Range Aggregation Does Not Feed the Name Index

**Type: Defect** / **Confidence: High**

**Location**

[Step 3 of `name-index-store`](../plans/name-index-store.md#s-3) (lines 122-125), which names only `walk`, the sweep, and `complete_scan`.
The file branch is [`TimelineScanner::scan_background`](../../daemon/entrypoints/daemon/src/service/timeline/scanner.rs#L111).

**What is wrong**

When a range aggregation targets one file, the scanner lists the parent folder and processes the media candidates; it does not enumerate the parent for the name index.
The plan's condition 3 says a range aggregation adds the Entries of the folder it enumerates, but the step never writes them for this branch.

**Basis**

`scan_background` has a separate `Ok(meta) if meta.is_file()` branch that calls `self.list` and `self.process`.
`walk` is not entered for that branch.
Step 3 lists `scanner.rs#L137` and `scanner.rs#L129` only.

**Impact**

A file uploaded or copied into an existing folder is not searchable from the index until the next full aggregation.
The plan's "follows our own changes" promise is narrower than its condition.

**Handling**

The owning plan is revised: Step 3 also replaces the parent's children for the single-file branch.
A mutation test covers upload and copy into a folder.

<a id="r-4"></a>
### R-4. The Name Index Stores Too Little to Answer Media and Archive Conditions

**Type: Design issue** / **Confidence: High**

**Location**

The stored columns at [Step 1 of `name-index-store`](../plans/name-index-store.md#s-1) (line 90), the unrated query at [Step 2 of `name-index-search`](../plans/name-index-search.md#s-2) (line 106), and the unrated start at [Step 4](../plans/name-index-search.md#s-4) (line 130).
The existing kind is [`FsEntryKind`](../../daemon/modules/engine/src/model/fs_entry.rs#L59).
The folder-like definition is in [`terms.md`](../terms.md) (line 35).

**What is wrong**

The store keeps a "kind", which in this codebase is `File`, `Dir`, or `Link`.
The search plan needs "image and video rows" for the unrated condition, and the listing rules need the archive hint for `foldersOnly` and `foldersFirst`.
`File` alone cannot distinguish an archive from an ordinary file, or an image from a text file.
Natural-order sorting also needs the original name, which the index does not store; the plan reads it back from the attributes, so the limit cannot be applied before that read.

**Basis**

`FsEntryKind` has three variants and an archive is a `File` with an `archive` hint.
The terms document defines a folder-like Entry as one whose kind is folder or whose archive hint is true.
The unrated condition in Rating and Tag Design §7.1 selects only images and videos.
The listing design says an index answer sorts by the same rules as other snapshots.

**Impact**

The index path cannot filter `foldersOnly` or `foldersFirst` without reading every candidate's attributes.
The unrated condition would either be wrong or fall back to a full file-system read, which contradicts the latency purpose.
The limit and `totalCount` would also be computed over the wrong candidate set.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1 and §5.2 as a decision on the index's columns.
Step 1 and Step 2 are revised together: the index carries the media kind and the archive hint, or these conditions are excluded from the index path and documented as walks.

<a id="r-5"></a>
### R-5. A Recursive Listing from a Hidden Start Can Be Answered from the Index

**Type: Design issue** / **Confidence: High**

**Location**

The contents rule at [Listing and Search Design §5.1](../design/listing.md#51-name-index) (lines 172-173) and the index-answer conditions at [§5.2](../design/listing.md#52-answering-recursive-listings-with-conditions) (lines 204-214).
The plan's condition 1 is at [`name-index-search`](../plans/name-index-search.md#s-1) (line 31).

**What is wrong**

The index does not hold hidden Entries or the Entries inside them.
The §5.2 conditions require only that the start is a local folder, not that the start path is free of hidden segments.
A start under a hidden folder therefore satisfies every condition and is answered from an index that has no rows there.

**Basis**

The index's contents rule excludes hidden Entries and their contents.
The current walk filters each Entry by its own name, so a listing that starts inside a hidden folder can return non-hidden children.
The plan's condition 2 and the notice in condition 7 do not mention a hidden start.

**Impact**

The index answer can be empty while the walk returns Entries, or the answer can omit all visible children.
The client can also show the "index is being built" notice for a start where the walk is the intended answer.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.2: the index answers only when the start path has no hidden segment.
The search plan adds this case to condition 2 and to the notice's exclusions in condition 7.

<a id="r-6"></a>
### R-6. The Search Plan's Equality Condition Collides with the Walk's Limit

**Type: Defect** / **Confidence: High**

**Location**

Conditions 1 and 5 of [`name-index-search`](../plans/name-index-search.md#s-1) (lines 31 and 35).
The walk's limit is in [`ListingEntries::scan`](../../daemon/entrypoints/daemon/src/service/listing.rs#L250), and the limit is supplied by [`LibraryBrowser::list_folder_entries`](../../daemon/entrypoints/daemon/src/service/library.rs#L66).

**What is wrong**

Condition 1 compares an index answer with "a walk of the same tree with no external changes".
On the 10-million-Entry fixture, the walk stops at `recursive_max_entries` (200,000 by default), while the index answer counts matches.
Condition 5 says the index answer is not truncated when matches are fewer than the limit.
Both cannot hold on the same Library.

**Basis**

`ListingEntries::scan` receives `max_entries` and stops there.
The design's §6 says a walk is cut by walked Entries and an index answer by matches.
The plan's condition 1 does not restrict the comparison to a Library smaller than the limit.

**Impact**

The acceptance test cannot pass as written.
If the test uses the 10-million fixture, condition 1 fails whenever a match lies beyond the walk's first 200,000 Entries.
If it uses a small Library, it does not exercise the condition 5 case.

**Handling**

Condition 1 is restricted to a Library smaller than `recursive_max_entries`, or to a walk performed without the limit.
The measurement and truncation case is tested separately under condition 5.

<a id="r-7"></a>
### R-7. "Current Sizes and Times" Is Not Guaranteed for a Cached Index Snapshot

**Type: Defect** / **Confidence: High**

**Location**

Condition 3 of [`name-index-search`](../plans/name-index-search.md#s-1) (line 33).
The freshness rules are [Listing and Search Design §4.3](../design/listing.md#43-freshness) (lines 126-129) and [§5.2](../design/listing.md#52-answering-recursive-listings-with-conditions) (lines 216-218).

**What is wrong**

The plan says an index answer "drops a match whose Entry was deleted externally after aggregation, and returns current sizes and times".
The attributes are read only when the snapshot is built.
A recursive snapshot has no per-request version check and is reused until `snapshot_max_age_secs`.
A deletion after the build is therefore not dropped until the snapshot is rebuilt.

**Basis**

The design says the attributes of matching Entries are read from the file system before building the snapshot.
It also says a recursive snapshot is checked by elapsed time alone.
`ListingSnapshots::get_or_scan` returns a fresh cached snapshot before running the scan closure.

**Impact**

The condition overpromises and a test that waits inside the age window will fail or will force an invalidation the product does not perform.
A user can see a deleted Entry for up to the snapshot age.

**Handling**

Condition 3 is reworded to "as of the snapshot build", and the test uses a fresh snapshot after the external deletion.
If per-request freshness is required, that is a different design decision and belongs in Listing and Search Design §4.3.

### R-9. The Name Index's Performance Acceptance Is Not Grounded

**Type: Design issue** / **Confidence: High**

**Location**

Condition 6 and [Step 6 of `name-index-store`](../plans/name-index-store.md#s-6) (lines 34-35 and 161-164).
The aggregation walk is at [`TimelineScanner::walk`](../../daemon/entrypoints/daemon/src/service/timeline/scanner.rs#L132).

**What is wrong**

The plan runs three full aggregations on the same index and takes the median.
The second and third runs update an existing index, so they measure upserts, not the first build.
A daily full aggregation still replaces every folder's children, so the steady-state cost can be a rewrite of close to 10 million rows.
The 200-bytes-per-Entry budget has no calculation or sample measurement behind it, and the fixture is on a local SSD while the design's target is a NAS.

**Basis**

`replace_children` is defined per folder; at about a million folders it implies a large number of transactions if the plan does not batch them.
The FTS5 trigram index stores every three-character sequence; the knowledge document covers matching behavior, not size.
The plan's own measurement procedure uses three runs on the same index.

**Impact**

The 20% ratio and the 200-bytes budget can both pass or fail for reasons unrelated to the first build.
If the index rewrites every row on every scan, the cost also affects the NAS's disk and the aggregation time every day, not only once.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1 and to the measurement procedure: the first build is measured separately, the steady-state full scan is measured with its own ratio, batching and transaction boundaries are part of Step 1, and the size budget is based on a sample measurement.

<a id="r-10"></a>
### R-10. A Disabled Name Index Causes a Full Aggregation on Every Startup

**Type: Design issue** / **Confidence: Medium**

**Location**

Condition 5 of [`name-index-store`](../plans/name-index-store.md#s-1) (line 34) and [Step 2](../plans/name-index-store.md#s-2) (line 113).
The startup rule is [Timeline Design §6.3](../design/timeline.md#63-when-aggregation-starts) (lines 172-177).

**What is wrong**

If the index cannot be opened or written, the plan passes a disabled index.
`is_usable` is then always false, so the next startup starts a full aggregation.
`mark_usable` cannot succeed on the disabled index, so the condition repeats on every boot.

**Basis**

The plan says to pass a disabled index when it cannot be opened.
The timeline's startup rule starts a full aggregation when the name index is not usable.
The plan has no distinction between "not built yet" and "cannot be used in this environment".

**Impact**

On a host whose listing directory is unwritable, a 10-million-Entry Library is fully scanned at every startup and is never marked usable.
The timeline index may still have files, so only this condition triggers the scan.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1 and Timeline Design §6.3: "not built" and "unusable in this environment" are separate states.
The plan's Step 2 records the reason the index is disabled.

<a id="r-11"></a>
### R-11. The Name Index's Generation Can Collide After the Timeline Index Is Lost

**Type: Design issue** / **Confidence: Medium**

**Location**

The per-Library generation at [Step 1 of `name-index-store`](../plans/name-index-store.md#s-1) (lines 90-95).
The timeline generation is at [`TimelineIndex::begin_scan`](../../daemon/entrypoints/daemon/src/service/timeline/index.rs#L301).

**What is wrong**

The plan does not say whether the name index's generation is its own sequence or the timeline's.
If it reuses the timeline's sequence, losing `state_dir/timeline/index.db` restarts the timeline generation at 1.
`state_dir/listing/names.db` is a separate file and can survive that loss, and rows from an older generation 1 can survive the sweep.

**Basis**

`begin_scan` inserts 1 when no row exists and increments otherwise.
The design says the timeline index is rebuildable and can be lost independently.
The name index is a separate SQLite file under the listing directory.

**Impact**

After a timeline-index loss, stale name rows can remain in an index that is still marked usable.
The impact is limited to the generation that collides, but the index has no second check that would detect it.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.1: the name index owns its generation sequence or a random epoch, and a full reset of the timeline index cannot make old name rows survive.

### R-12. `indexed` Is Not Stored in the Snapshot

**Type: Defect** / **Confidence: High**

**Location**

[Step 1](../plans/name-index-search.md#s-1) (line 94) and [Step 3](../plans/name-index-search.md#s-3) (line 118) of `name-index-search`.
The snapshot cache is [`ListingSnapshots::get_or_scan`](../../daemon/entrypoints/daemon/src/service/listing/snapshot.rs#L242).

**What is wrong**

The plan says the existing walk returns `false` and the index path sets `true`.
A listing snapshot is cached and returned without running the scan closure, so a response that recomputes `indexed` from the current path or the current index usability can lie about how the cached snapshot was built.

**Basis**

`get_or_scan` returns a cached snapshot before calling the closure.
The snapshot currently holds the Entries and the truncated flag; it does not hold a provenance flag.
The plan does not say where `indexed` lives or how it survives a cache hit.

**Impact**

A walk snapshot built while the index was unusable can be returned after the index becomes usable and be reported as `indexed: true`, or the reverse.
The client's notice appears or disappears for the wrong reason.

**Handling**

The owning plan stores the provenance in `ListingEntries` or `ListingSnapshot` at build time and returns it with the cached snapshot.
A test builds a walk snapshot, makes the index usable, and confirms that `indexed` stays false for the cached snapshot.

### R-13. The Order Used to Stop at `recursive_max_entries` Is Undefined

**Type: Design issue** / **Confidence: Medium**

**Location**

[Step 3 of `name-index-search`](../plans/name-index-search.md#s-3) (line 118) and [Listing and Search Design §6](../design/listing.md#6-recursion-limit) (lines 228-238).

**What is wrong**

The step stops at `recursive_max_entries` matches, but it does not define the order in which matches are taken, or how `totalCount` and `truncated` are computed when there are more matches.
For a walk, the design says the storage layer's walk order decides and that it has nothing to do with the sort order.
There is no equivalent rule for an index query.

**Basis**

The index query returns rows in some order chosen by the implementation.
The snapshot is sorted for paging.
If the limit is applied before sorting, the retained subset is not the first page of any defined order.

**Impact**

A truncated index answer can contain an arbitrary subset, and `totalCount` can disagree with what the user would see from a walk.
The behavior is stable only if the query order is stable, which the plan does not require.

**Handling**

Destination (not yet transcribed): Listing and Search Design §5.2 and §6: the index path defines the order used for the limit, and whether `totalCount` is an exact count or a bounded count.
The search plan's test covers a match count above the limit.

### R-14. The Search Purpose and Condition 6 Disagree on Broad Matches

**Type: Defect** / **Confidence: High**

**Location**

The purpose at [`name-index-search`](../plans/name-index-search.md) (line 27) and condition 6 (line 36).
The attribute read is described at [Listing and Search Design §5.2](../design/listing.md#52-answering-recursive-listings-with-conditions) (lines 216-219).

**What is wrong**

The purpose says a search of three or more characters returns its first page within a second.
Condition 6 restricts the measurement to terms matching at most 1,000 Entries.
A three-character term can match far more, and the design reads the attributes of all matches before building the snapshot.

**Basis**

The snapshot holds only matching Entries, but its attributes are read before the page is cut.
The limit caps the number of matches at 200,000, not the attribute reads.
The plan's own condition 6 limits the measurement to a small match set.

**Impact**

The acceptance can pass while the stated purpose fails for a common broad term.
The user-visible promise and the measured promise describe different searches.

**Handling**

The purpose and condition 6 are aligned: either the purpose is limited to narrow matches, or the plan defines how a broad match returns its first page without reading all attributes.
The decision is to be transcribed to Listing and Search Design §5.2.

### R-15. The Search Measurement Measures Snapshot Hits and a Local SSD

**Type: Improvement proposal** / **Confidence: Medium**

**Location**

[Step 6 of `name-index-search`](../plans/name-index-search.md#s-6) (lines 153-157).
The snapshot reuse is at [Listing and Search Design §4.1](../design/listing.md#41-the-unit-that-is-built) (lines 85-99).

**What is wrong**

The plan runs 20 searches per term class.
If the same term is repeated, the later searches hit the in-memory snapshot and do not measure the index query.
The fixture is on a local SSD, while the design's operating premise is a NAS.
Cold and warm page caches are not separated.

**Basis**

A recursive snapshot is reused until `snapshot_max_age_secs` or an invalidation.
The plan does not say whether the 20 searches use different terms or clear the snapshot.

**Impact**

The p95 can be dominated by cached responses and by local-disk latency.
It does not support the purpose's claim for the target environment.

**Handling**

The measurement procedure uses distinct terms or clears the snapshot between searches, separates the first query from later pages, and records the environment and the cache state.
This is a plan revision, not a product defect.

### R-16. Attribute Reads on the Index Path Have No Budget or Cancellation

**Type: Design issue** / **Confidence: Medium**

**Location**

[Step 3 of `name-index-search`](../plans/name-index-search.md#s-3) (line 118) and [Listing and Search Design §5.2](../design/listing.md#52-answering-recursive-listings-with-conditions) (line 217).

**What is wrong**

The plan says to read the attributes of the matches with the detail batch's workers.

**Type: Improvement proposal** / **Confidence: Medium**

### R-26. Acceptance Commands Use an Escaped Pipe and Cannot Detect the Stale Text

**Type: Defect** / **Confidence: High**

**Location**

The fourth row of [the LAN plan's acceptance table](../plans/lan-plaintext-exposure.md#6-acceptance-checks) (line 115).
The eighth row of [the search plan's acceptance table](../plans/name-index-search.md#6-acceptance-checks) (line 167).
The fifth row of [the thumbnail plan's acceptance table](../plans/representative-thumbnail-refresh.md#6-acceptance-checks) (line 156).

**What is wrong**

All three commands write an alternation as `a\|b`.
Ripgrep treats the escaped pipe as a literal `|`, not as alternation, so the pattern never matches either target sentence.
The LAN command exits 1 without checking that `127.0.0.1` is absent or that Tailscale is mentioned.
The search command returns no match even when the three stale current-state sentences are still present, so it cannot fail.
The thumbnail command has the same empty pass for the stale header sentence.

**Basis**

We ran `rg -n '127\.0\.0\.1\|Tailscale'` on a file containing both lines: it printed nothing and exited 1.
The same file with `rg -n '127\.0\.0\.1|Tailscale'` printed both lines and exited 0.
The other two commands use the same escaped pipe.
The implementation-plan norm requires an acceptance command to be able to produce its expected result.

**Impact**

The acceptance can pass while the old text remains.
Condition 4 of the LAN plan is not checked at all, and conditions 8 and 5 of the other plans lose their only guard against stale prose.

**Handling**

The three commands use an unescaped `|`, multiple `-e` patterns, or separate commands, and the expected result is written so that the command can actually produce it.
The plan is revised; the review remains open until the commands are corrected.
